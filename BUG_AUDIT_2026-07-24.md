# SudokuPro — Bug Audit + Engine Verification (2026-07-24)

Method: five parallel source audits (model, game/websocket, feature services, auth/config/deploy,
clients) followed by an **independent game-playing engine** (`engine/Engine.java`) that drives the
*real* model classes — generating boards, solving them with its own backtracking solver, playing the
winning moves, and probing erase/undo/redo/snapshot/mirror paths. Findings below are split by how they
were verified.

The engine result: **12 invariant suites, 6 model bugs reproduced.**

**Current status after 12 hardening passes:** 291 JUnit tests green; model engine **40
invariants** / 0 bugs; **live engine 111 invariants** / 0 bugs; adversarial suite 41/41;
fuzz suite 28/28. All FOUR harnesses run in CI on every push (`harness` job in
`.github/workflows/ci.yml`).

## CONFIRMED — reproduced by the engine (ran against real model code)

### C1 · P0 · Every game has the *same* solution
`model/SudokuBoard.java:508` (`solve`) fills the grid trying values 1→9 in fixed order, so
`new SudokuBoard(difficulty,…)` — the path `GameService.createNewGame` actually uses (`GameService.java:118`)
— always produces the **one lexicographically-first completed grid**. Only clue *positions* vary.
Engine proof: 5 fresh d3 games → 1 distinct solution; a d1 and a d5 game share the identical answer.
Anyone who solves a single daily/duel/game knows the solution to all of them. (The randomized
`SudokuGenerator` exists but is not wired into new-game creation.)

### C2 · P1 · A wrong entry can never be erased through the move path
`SudokuBoard.isValidMove(r,c,0)` scans the row/col/box for a cell equal to `0`; on any unfinished board
an empty cell always exists, so a clear is always "invalid". `makeMove`, `applyExternalMove`,
`applyBatchMoves` (the WebSocket move path) and the clients' clear / "Fix Conflicts" actions all no-op.
Only a server `undo` can remove a value.

### C3 · P1 · Auto-solve reward guard launders through undo/redo
`undo()`/`redo()` call the single-arg `SudokuCell.setValue(int)`, which resets `MoveSource` to `UNKNOWN`.
Engine proof: a board finished with an `AUTOSOLVE` cell reports `hasAutosolvedCells()==true`, but after a
full undo→redo replay it reports `false` — so an AI-solved board can be replayed into a "legit" solve that
passes the A-4 anti-reward guard and mints gems/streaks/achievements.

### C4 · P2 · undo/redo lose hint/source provenance
Same root cause as C3, user-visible: `makeMove(HINT)→undo→redo` leaves the cell's source `UNKNOWN`, so hint
coloring and provenance are lost after any undo/redo.

### C5 · P2 · `applyBatchMoves` over-counts moves
`SudokuBoard.java:430` does `moveCount += moves.size()` unconditionally, even though the loop skips rejected
moves. Engine proof: a 5-move batch with 2 invalid moves still added 5. `jumpToMove`/`loadReplayFromJson`
inherit the inflation; anti-cheat/scoring keyed on `moveCount` drifts.

### C6 · P2 · undo after a solve leaves a stale `solved` flag
`undo()` never recomputes `solved`. Engine proof: solve → undo one cell → `isSolved()==false` but the
persisted `solved` flag stays `true`. A board persisted in that state has `solved=true` in the DB, so
`GameRepository.findResumableByPlayerId` (filters `solved=false`) permanently hides the now-unsolved game
from the resume/saved list.

## LIVE PLAYTHROUGH — 2026-07-25 (real server + real Redis + real browser)

Booted the actual Spring Boot server (H2 + Redis 7 on localhost, dev profile) and drove the
shipped `/play/` client in headless Chromium. This both **proved** the P0s below and surfaced
two further total-breakage bugs that only appear when you actually run the thing.

**P0 reproduced exactly as predicted.** With Redis UP on a single replica, nobody else touching
the game: `GET /api/game/hint`, `POST /{id}/save`, `POST /{id}/solve` each stalled **3.1s** then
returned **HTTP 500** — `"busy on another server instance"`. With Redis stopped, the same calls
succeeded. Server log: `Game <id> redis lock held by another replica past 3000ms wait budget`.
WebSocket moves failed the same way. **Gameplay was completely impossible with Redis running.**

**NEW P0 — the browser client could never make a single move (any Redis state).**
`WebSocketController` deserialized the move payload straight into `EnhancedMove`, whose canonical
constructor does `requireNonNull(source)`. The web client sends `{row,col,oldVal,newVal}` with no
`source`, so every move threw `MoveSource cannot be null` and returned an error envelope.
Measured: a full 28-cell solve attempt had **28/28 moves rejected**. The suite missed it because
the only sourceless-payload test is the spectator case, which is rejected *before* parsing.

**NEW P1 — the documented entry point 404'd.** README says open `http://localhost:8080/play/`.
Boot only resolves a directory welcome page for the context root, never a static sub-directory, so
`/play/` returned 404 → forwarded to `/error` → which required auth → surfaced as a bare **401**.
`/play/index.html` worked. The zero-install client looked like it was behind a login wall.

**NEW P1 — every registered player started on 0 gems, so Hint was permanently dead.**
`EconomyService.walletFor` grants the 15-gem signing bonus only in its `orElseGet` (i.e. only when
it creates the row), but registration creates the row first. Hints cost 5 → new accounts got
`402 Not Enough Gems` forever. Observed live: fresh account, `gems: 0`.

**Also observed:** `SudokuGenerator` repeatedly fails to build HARD boards — 10 occurrences of
`Failed to remove enough cells for difficulty: 55..58/60` in one startup, i.e. the 60-removal tier
regularly exhausts its attempt budget (`EventEngine`'s hourly duels log
`Cosmic duel failed to erupt`). Not yet fixed.

### Fixed in this pass (all verified live, full suite green at 180 tests)

| Fix | Evidence |
|---|---|
| `GameLockManager` nested re-entry — reuse the outer Redis lock when the same thread re-enters (`getHoldCount() > 1`) | save/solve went 3.1s→500 to **0.1s→200**; zero lock warnings |
| `WebSocketController.readClientMove` — parse move fields directly; server always stamps `PLAYER` (a client must not be able to claim `HINT`/`AUTOSOLVE`, which the reward guards key on) | **28/28 moves applied** |
| `WebClientMvcConfig` — forward `/play` and `/play/` to the client shell | `/play/` **401 → 200** |
| `/error` permitted in `SecurityConfig` | anonymous 404s no longer masquerade as 401 |
| `AccountService` — grant starting gems on genuinely new accounts (claiming an existing wallet row still keeps its gems) | fresh account now **15 gems**; hint charges 5 → 10 |

**End-to-end result:** register → login (15 gems) → new Easy game (53 clues) → hint (−5 gems) →
solve all 28 cells through the UI → SOLVED overlay + `gameEnd` + `ACHIEVEMENT` + 10 gems awarded.
**Zero JS errors, zero non-2xx responses.**

> Visible in the final screenshot: the solved grid's top-left box reads 1,2,3 / 4,5,6 / 7,8,9 —
> the deterministic-generator bug (C1) showing through on a real solve.

## HARDENING PASS 2 — 2026-07-25 (adversarial + load testing on a live server)

Ran a 20-check black-box adversarial suite (`testing/adversarial_api_test.py`), a reward-replay
probe (`testing/reward_replay_probe.py`), and the load-test harness against the running server.
Four more real bugs, all now fixed with regression tests. Suite: **180 → 193 tests, green.**

**P0 — unbounded currency farm via replayed `/end` (V2, now proven and fixed).**
Solved a board legitimately over the gameplay WebSocket, then replayed
`POST /api/game/{id}/end`: **+15 gems and +15 XP on every single call**, 15 → 135 gems in seven
requests. `endGame` guards on `activeGames.remove() != null`, but the endpoint's own ownership
check calls `getGame` first, which re-hydrates the finished board — so the guard never held.
Fixed with a persisted `rewards_granted` flag (Flyway `V7`), set only on SOLVED ends so that
abandoning a game and finishing it later still pays out. Re-verified live: balance now flat
across seven replays.

**P1 — hint on another player's board drained THEIR wallet (V3, now proven and fixed).**
`getHint` charged `board.getPlayerId()` with no caller check. Bob requesting a hint on Alice's
gameId: Alice 15 → 10 gems, Bob unchanged, Bob got the hint — plus Alice's `hintCount` rose,
costing her the clean-solve bonus. Now the caller is passed through and a non-owner gets 403.

**P1 (security) — brute-force lockout was completely non-functional.**
A wrong password returned **HTTP 500**, not 401. Spring auto-registers a third
`DaoAuthenticationProvider` from the `UserDetailsService` bean using the default
`DelegatingPasswordEncoder`, which requires an `{id}` prefix; our hashes are raw `$2a$…`, so it
threw `IllegalArgumentException: no PasswordEncoder mapped for the id "null"`. A *correct*
password matches on the first provider and never reaches it, which is why this was invisible.
Because `IllegalArgumentException` is not an `AuthenticationException`, `ProviderManager`
published no failure event, `LoginAttemptEventListener` never counted the attempt, and the
documented "5 failures in 60s → 429" lockout **never engaged**: nine consecutive wrong passwords
all returned 500. Fixed by publishing the BCrypt encoder as a bean. Verified: 5× 401 then 429.

**P1 — HARD difficulty could never generate a puzzle.**
`Difficulty.HARD` asked for 60 removals (21 clues). Measured over 25 grids, an exhaustive
shuffled sweep tops out at **55–58 removals** — so HARD failed **0/20**, and EXTREME (70) and
NIGHTMARE (80) were below the proven 17-clue minimum, impossible by construction. This is the
source of the `Cosmic duel failed to erupt` errors. Fixed twice over: the removal loop is now a
shuffled single pass over all 81 cells (was `cellsToRemove * 2` random samples, which ran dry as
the grid emptied), and the ladder is now 40/48/52/54/55. All five tiers: **20/20 generate.**

**Coverage gap closed.** `SecurityConfig` is `@Profile("!test")`, so no test had ever exercised
the real auth rules — Boot's default chain ran instead. Added `SecurityRulesTest` (7 tests, runs
under `dev`) covering the public surface, protected APIs, admin role, CSRF enforcement, and the
security headers.

**Load test.** 25 concurrent players, 621 move round-trips, **zero errors**
(`move_roundtrip` p50 504ms / p95 518ms, `register` p50 108ms, `session` p50 105ms).

> Confirmed the shared-IP lockout finding by accident: a load-test run immediately after the
> brute-force probe had **all 25 players fail at `session`** — `LoginAttemptLimiter` keys on
> `getRemoteAddr()` with no `X-Forwarded-For` handling, so one bad actor locks out everyone from
> that address. Behind a k8s Service or ingress every user shares one source IP. Still open.

## HARDENING PASS 3 — 2026-07-25 (competitive + persistence subsystems)

Two deep audits of subsystems that had never been reviewed adversarially, then live verification.
Three more bugs fixed, two of them the most severe found in the whole engagement.
Suite: **193 → 199 tests**, adversarial harness **20 → 27 checks**, all green.

### P0 — `POST /api/game/{id}/solve` had NO ownership check (fixed)

The single most damaging hole. Competitive game ids are fully deterministic and usernames are
public from the leaderboards — `duel-<id>:<player>`, `daily-<date>:<player>`,
`week-<year-Www>-p<n>:<player>` — so one request could AI-fill and **persist** any player's board.
The victim then cannot move (grid full), cannot resume (409), and **can never claim the win**,
because the auto-solve reward guard suppresses their completion. The response also returned the
finished grid, so it doubled as a solution oracle.

**Verified live, attacker vs victim:** `/solve` on the victim's game → `HTTP 200`, victim's board
went 53 → 81 filled, `solved=true`, and the attacker received all 81 cells.

**And it reached the shared templates.** The daily/weekly template rows are ordinary boards:

```
victim joins daily                                  -> 200
attacker POST /api/game/daily-2026-07-25/solve      -> 200   TEMPLATE POISONED
brand-new player POST /api/daily/join               -> 81/81 filled, solved=true
```

One request destroyed the day's puzzle for the **entire player base** — every later joiner got a
pre-solved, unwinnable board, persisted. The same applies to the five weekly templates, which
would void a whole tournament week. Now owner-only; re-verified: 403, victim untouched, later
joiners get a proper 33/81 puzzle.

### P0 — every played board was unreadable from the Redis cache (fixed)

`SudokuBoard` serializes `getReplayHistory()`, and each element is an `EnhancedMove` whose bean
alias `getValue()` emitted a `"value"` property the record's canonical creator does not accept.
`@JsonIgnoreProperties` sits on `SudokuBoard`, not on the nested record, so deserialization threw
`UnrecognizedPropertyException: "value"` for **any board with at least one move**.

`GameService.getGame` does not guard the Redis read (unlike `saveToRedis`, which is carefully
wrapped), so the exception propagated instead of falling back to the database: every read of a
played game 500'd for the full 60-minute TTL once it left the in-memory active set — a pod
restart, an eviction, or simply a second replica. Reproduced directly against the model jar:

```
CASE A zero-move board        round-trip OK
CASE B after ONE move         FAILED: UnrecognizedPropertyException -> "value"
```

Fixed with `@JsonIgnore` on the alias plus `@JsonIgnoreProperties(ignoreUnknown)` on the record so
existing cache entries still load. Re-verified: both cases round-trip.

### P1 — the archive was a solution oracle for today's puzzle (fixed)

`joinArchive` rejected only *future* dates, so today was a legal archive date. An archive copy is a
throwaway (its id shape earns no streak or leaderboard credit), so the play was: archive-join
today → auto-solve that copy → read the completed grid → join the real daily → type in the answers
for a top leaderboard time. Archive now requires a strictly past date (verified: 404).

### Still open from these audits (not fixed)

- **No optimistic locking on `User`** (no `@Version`): concurrent hints on two different games
  serialize on different per-game locks, so both can charge the same 5 gems — N hints for one
  payment. `PowerUpService.use` takes no lock at all, so one held unit can be spent twice.
- **Season rollover mislabels the champion**: the badge is stamped with the *incoming* season id
  while scoring the *outgoing* ladder, so nobody ever holds a badge for the season they won, and
  the genuine winner can never receive it (the key is already taken).
- **Season soft-reset only touches the top 100** despite the javadoc promising every rated player,
  so the un-reset tail eventually outranks the compressed head.
- **`activeGames` grows without bound on the read path** — `getGame` puts without trimming, and
  abandoned games are never evicted; `GameLockManager.localLocks` leaks in lockstep.
- **`releaseGame` is called while the lock is still held** (`endGame`, `trimActiveGames`), so a
  concurrent arrival gets a brand-new monitor for the same game.
- **Duplicate `sudoku_boards` rows**: `game_id` has no unique constraint and join/accept probe
  without holding a lock, so a double-click can insert two rows and then `findByGameId` throws
  permanently for that id.
- **`trimActiveGames` evicts an arbitrary entry**, not the oldest, and leaves the Redis key behind.
- **`snapshotCells` drops `strategy`**, so `cosmicDripLevel` silently resets to 0 after any restore.
- **Shutdown persists every board the pod ever *read***, which can roll a game back to a stale state.

## HARDENING PASS 4 — 2026-07-25 (realtime layer + hostile-input fuzzing)

A deep audit of the WebSocket/realtime layer plus a new 28-check hostile-input fuzz suite.
Six more bugs fixed. Suite **199 → 204 tests**; adversarial **27/27**, fuzz **28/28**.

### P0 — WebSocket `sync` was a solution oracle for every shared puzzle (fixed)

`rejectSpectator` guarded `move`/`undo`/`redo` but **not** `sync`, and the handshake let any
authenticated principal attach to any gameId. Daily, weekly and duel boards are per-player
copies of ONE shared grid, so another player's copy is an answer key for the puzzle you are
racing them on — and `sync` returns all 81 cell values.

**Verified live:** the attacker connected to `daily-<date>:<victim>` and received the
victim's **53/81 in-progress board**. In a ranked duel this streams the opponent's board
move by move. Fixed by refusing spectator connections to `daily-`/`week-`/`duel-` games;
free-play spectating (a deliberate feature) is untouched.

### P0 — one client could lock any player out of their own game (fixed)

`handleTextMessage` called `getGame` — which takes the cross-replica game lock, a Redis
`SET NX` + Lua `DEL` round-trip — for **every inbound frame, including unknown types**, and
there was no rate limit anywhere on the WebSocket path. A spectator looping junk frames
could hold that lock continuously and starve the board's owner, who would then fail every
move/hint/undo with "busy on another server instance" after a 3s stall — the same outage
symptom the nested-lock fix removed, now weaponisable against a chosen victim. Fixed with a
per-session token bucket (40 burst, 20/s) applied *before* the game is touched.

### P1 — every board broadcast was 25 KB, and 3x over the frame limit (fixed)

`SudokuCellView` is a record, but Jackson also serializes public no-arg getters — so each of
the 81 cells emitted `displayValue`, `timestampString`, `hintDisplay`, `empty`, `conflicted`,
`hasPencilMarks` **and the entire eight-key `toAnalyticsMap()` nested object**. A single
`BoardState` measured **25,729 bytes**, against Tomcat's 8 KB default WebSocket buffer, and
it is pushed to every session in the game on every sync/undo/redo, on every replica. It also
put server-side analytics shape on the public wire. `@JsonIgnore` on the derived accessors
cut it to **16,545 bytes (−36%)**.

### P1 — oversized frames silently killed the connection (fixed)

Found by fuzzing: a 16 KB frame closed the socket with 1009 *"too big for the output
buffer"* and left it unusable — the container rejects the frame before the handler runs, so
application-level truncation cannot help. Limits are now set per session
(`setTextMessageSizeLimit`). Note a `ServletServerContainerFactoryBean` is the wrong fix
twice over: it configures the JSR-356 container, which Spring's raw WebSocket stack does not
consult, and it requires a real embedded container, breaking every MockMvc test context.

### P2 — friend request to a non-existent player returned 200 (fixed)

Fuzzing got `HTTP 200` for a friend request to an emoji username, writing a pending entry
and a 14-day Redis key for an account that will never exist — unbounded attacker-controlled
key growth. Now 400.

### P2 — abnormal disconnects never told peers (fixed)

`leave` was broadcast only from `afterConnectionClosed`, which bails early because
`handleTransportError` has already removed the `playerMap` entry. So any TCP reset, proxy
timeout, pod eviction or client crash left the departed player rendered as still present on
every other client, permanently. Also: `join` relayed the caller's entire raw envelope to
every peer (arbitrary attacker JSON) — now only the identity — and chat is capped at 500
characters before fan-out.

### Fuzz coverage added (`testing/fuzz_edge_cases.py`)

25 HTTP cases (negative/huge/non-numeric difficulty, path traversal, 10k ids, null bytes,
unicode, malformed and deeply-nested JSON, 100k share codes, boundary limits, reserved and
oversized usernames) and 17 hostile WebSocket frames (empty, plain text, `null`, arrays,
missing/typed-wrong fields, out-of-range and string coordinates, control characters, 20k
chat, unknown types, 200-deep nesting). The session must survive every frame and still be
functional afterwards.

## HARDENING PASS 5 — 2026-07-25 (backlog clear-down: economy race + core move semantics)

Worked the known-open list. **The engine harness is now fully green for the first time:
26 invariants, 0 bugs** (it started this engagement at 7). Suite **204 → 213 tests**.

### P1 — concurrent hints oversold the wallet (fixed)

`chargeForHint` was a read-modify-write, and hint charging is serialized only by the
PER-GAME lock — so requests against DIFFERENT games never contended. **Verified live: six
concurrent hints across six games were all served for a total of 15 gems instead of 30** —
six hints for the price of three, with the balance driven to zero while every request
succeeded. Replaced with a single atomic conditional UPDATE
(`deductGemsIfAffordable`, `@CacheEvict` since `findByUsername` is `@Cacheable` and a bulk
update bypasses the persistence context). Re-verified: `[200, 402, 200, 402, 402, 200]` —
exactly three served, 15 gems spent.

### P1 — a player could not erase a wrong entry (fixed)

`isValidMove` scanned the row/column/box for a cell equal to the new value, and an
unfinished board always contains an empty cell — so a clear (`newVal 0`) was always read as
"a duplicate" and always rejected. That hit `makeMove`, `applyExternalMove`,
`applyBatchMoves`, and therefore the WebSocket move handler and both clients' erase
buttons. Only a server-side undo could take a value back. Verified live over the wire:
place 8, erase, cell reads 0.

### P1 — every game had the same solution (fixed)

`SudokuBoard.solve()` tried candidates 1..9 in fixed order, so generation was
deterministic: **every board ever created resolved to the same completed grid**, only the
clue positions varying. Solving one puzzle gave you the answer to every daily, duel and
tournament board. (It was visible in an earlier screenshot — the solved grid's first box
read 1,2,3 / 4,5,6 / 7,8,9.) Generation now uses a shuffled candidate order.

### P1 — auto-solved boards laundered through undo/redo (fixed)

`undo()`/`redo()` used the single-arg `setValue(int)`, which resets `MoveSource` to
`UNKNOWN`. Since `hasAutosolvedCells()` is exactly what suppresses rewards on an AI-solved
board, an undo/redo round trip turned an auto-solve into a "legitimate" solve that paid
gems, streaks and achievements. `Move` now carries the prior source and both operations
restore provenance.

### P2 — three more move-semantics defects (fixed)

- **Stale `solved` flag**: nothing ever cleared it, so undoing a cell on a finished board
  left `solved=true` while the grid was incomplete — and such a board is filtered out of
  `findResumableByPlayerId`, permanently hiding a game the player could still finish.
- **`applyBatchMoves` over-counted**: `moveCount += moves.size()` counted rejected moves;
  anti-cheat move-rate scoring reads that number.
- **Mirror mode undo desync**: one player action writes two cells and pushed two history
  entries, so a single undo reverted only the twin and left the primary cell filled. The
  pair is now one undo unit.

### P2 — `isValidMove` mutated the mistake heatmap (found by a new test, fixed)

A public predicate with a side effect: every `false` result incremented
`heatmapMistakeCounter`. It is called to *probe* legality — by the WebSocket handler before
applying, by the apply paths themselves, by the solver, and by clients listing candidates —
so a single rejected move counted twice, and merely asking "which digits fit here?" logged
a mistake per digit that did not fit. The heatmap gates `isPerfectClear()`, so probing could
silently cost a flawless solve. The predicate is now pure; mistakes are recorded only where
a move is genuinely rejected.

### Noted, not changed

`GET /api/powerups` reports four legacy inventory keys (`cosmicReveal`, `undo`,
`timeBoost`, `hint`) that are always zero and cannot be bought — the real catalog is
`EXTRA_LIFE`/`REVEAL_CELL`/`FREEZE`. Purchases were verified to track correctly under their
own keys, so this is confusing API output rather than a functional fault.

## HARDENING PASS 6 — 2026-07-25 (stability, lock lifecycle, season correctness, ops)

Cleared the remaining stability/correctness backlog. Suite **213 → 218 tests**.

### P1 — the board cache grew without bound (fixed)

`getGame` populates `activeGames` on a cache miss but never called `trimActiveGames()` —
only createNewGame/adoptGame did. Abandoned games are never evicted either, so a pod that
merely READ boards (spectating, `/api/game/{id}`, every `/end` ownership check) grew the
map, with `GameLockManager.localLocks` growing alongside it, until it ran out of memory.
Eviction also picked an arbitrary hash-order entry while calling it "oldest", so it could
discard the game someone was actively playing. Now: read path enforces the cap, and
eviction is genuine LRU via a `lastAccess` map.

### P1 — the lock entry was dropped while a thread still held it (fixed)

`releaseGame` unconditionally removed the monitor, and callers did so while HOLDING it —
`endGame` called it from inside its own try-with-resources, and `trimActiveGames` did the
same for evicted games. The next caller of `lock()` found no entry, `computeIfAbsent`
minted a BRAND NEW `ReentrantLock`, and two threads could occupy the same game's critical
section. `releaseGame` now refuses to drop a monitor that is locked or has queued threads,
and `endGame` reclaims it only after the lock is released.

### P1 — season champions were badged with the wrong season (fixed)

Rollover labelled the badge with `seasonId()` — the season now STARTING — while scoring the
outgoing ladder. With the clock in Q3 the Q2 winners were crowned
`SeasonChampion-2026-Q3`: nobody ever held a badge for the season they actually won, and
the genuine Q3 champion could never receive it because the key was already taken. Added
`previousSeasonId()`. The existing test had encoded the bug, asserting the wrong season.

### P1 — the soft reset only touched the top 100 (fixed)

Rollover iterated the same top-100 page it used for the podium, so from rank 101 down
nobody was reset. The un-compressed tail kept its full rating and, season after season,
permanently outranked the compressed head — inverting the ladder the reset exists to
refresh. Replaced with a single bulk `softResetDuelRatings()` over every rated player.

### P1 (ops) — a Redis blip crash-looped every pod (fixed)

Both k8s probes hit the aggregate `/actuator/health`, which includes the Redis indicator —
so a transient Redis outage made every pod report 503 and got the whole deployment
restarted, directly contradicting the "degrades gracefully without Redis" design (and it
genuinely does degrade: local locking, in-memory stores). Split into health groups:
liveness = game-engine self-test only, readiness = db + redis + engine.

**And a bug introduced by that fix, caught before shipping:** `SecurityConfig` permitted
only the exact `/actuator/health` path, so `/actuator/health/liveness` and
`/actuator/health/readiness` answered **401** — kubelet sends no credentials, so pods would
never have become ready and liveness would have restarted them forever. Matcher widened to
`/actuator/health/**`. Verified live end to end:

```
with Redis    liveness 200 UP    readiness 200
Redis stopped liveness 200 UP    readiness 503    (aggregate 503)
```

### P2 — the login lockout punished everyone behind one IP (fixed)

`LoginAttemptFilter` and Spring Security's `WebAuthenticationDetails` both key on
`request.getRemoteAddr()`. Behind the k8s Service every user arrives from ONE address, so
one attacker's five bad passwords would lock out the entire player base — and genuine
per-client limiting never worked. (Observed earlier: a load-test run straight after the
brute-force probe had all 25 players fail at `/api/session`.) Set
`server.forward-headers-strategy=NATIVE`, which fixes both call sites at once; Tomcat's
`RemoteIpValve` only honours `X-Forwarded-For` when the immediate peer is private-range, so
a directly-connected client cannot spoof around the limiter.

## HARDENING PASS 7 — 2026-07-25 (last of the known-open list)

Suite **218 → 220 tests**; engine harness still 26 invariants / 0 bugs. This closes every
item that was carried as "known-open".

### P1 — duplicate `sudoku_boards` rows could wedge a game id permanently (fixed)

`game_id` is the application's real identity for a board (the PK is a surrogate bigserial)
but nothing enforced uniqueness, and the join/accept paths probe-then-insert without
holding a lock across both steps. A double-clicked "Join daily", a retried POST, or two
replicas racing the day's first join could insert two rows with the same `game_id`.

That is not a cosmetic duplicate: `findByGameId` is a single-result query, so afterwards
every read that misses the per-pod cache throws `IncorrectResultSizeDataAccessException` —
not an `IllegalArgumentException`, so the callers' catch blocks don't handle it and
get/hint/save/resume/end all 500 **permanently** for that game.

Flyway `V8` dedupes then adds a partial unique index. **Validated against a real
PostgreSQL 16** by running the whole V1→V8 chain with three seeded duplicates:

```
rows before V8: 4   (3 duplicates + 1 unique)
rows after  V8: 2
survivor kept its grid snapshot: t
duplicate insert now: ERROR: duplicate key value violates unique constraint
```

The tie-break deliberately keeps the row that still has a `cells_json` grid, then the most
recent start, then the highest id — so dedupe never discards the playable copy.

### P2 — `cosmicDripLevel` silently reset to 0 on every restore (fixed)

`snapshotCells` omitted each cell's `strategy`, and `calculateCosmicDripLevel()` counts
cells whose strategy is COSMIC or STARFORGE — so any database or Redis round-trip
recomputed the drip level as zero. Added `st` to the snapshot; older snapshots without the
key restore unchanged.

### P2 — shutdown could roll a game back to a stale state (fixed)

`@PreDestroy` persisted **every** board in `activeGames`, but that map is a read-through
CACHE: it also holds boards this pod merely looked at (a spectator view, an ownership
check, an `/api/game/{id}` read). Writing those on shutdown could overwrite whatever
another replica had since saved. Every mutation already persists inline, so the shutdown
flush is now restricted to games this pod actually wrote (`locallyMutated`, recorded at the
single `persistBoard` choke point).

## HARDENING PASS 8 — 2026-07-25 (schedulers, anti-cheat, analytics, CI)

Suite **220 → 243 tests**; engine harness 26 invariants / 0 bugs; adversarial 27/27 and
fuzz 28/28 re-run green against a live server on Postgres 16 + Redis 7 after every change
below. This pass audited the three subsystems that had only ever been read once — the
cosmic event schedulers, the anti-cheat pipeline, and the analytics/metrics layer — and
then wired all three harnesses into CI so the next regression is caught by a build rather
than by hand.

### P1 — every scheduler tick installed another permanent repeating schedule (fixed)

`EventEngine.triggerDailyChallenge()`, `triggerCosmicDuel()` and `triggerDripShowdown()`
each called the *private* `scheduleX()` method, and every `scheduleX()` installs a fresh
`scheduler.scheduleAtFixedRate(...)`. `EventScheduler` calls the triggers on its own
cadence, so each tick added a permanent repeating task on top of the ones already running:
the firing rate compounded against a three-thread pool, reaching roughly 97 concurrent
drip-showdown schedules after a day.

Compounding it, each task body ended in `throw e`. `scheduleAtFixedRate` responds to a
thrown exception by **cancelling all subsequent executions and reporting nothing**, so any
single failure silently retired that event type for the pod's lifetime — the one branch
that could have relieved the pile-up instead killed the feature.

Split into `runX()` (one cycle) and `scheduleX()` (installs the repeat, wrapped in
`safeRepeat`, which logs and swallows). Verified live: exactly two firings of each event at
boot — one from `startCosmicEvents()`, one from the scheduler's immediate trigger — where
before the count grew monotonically. Pinned by `EventEngineTest` (3 tests).

### P0 — the entire anti-cheat subsystem could never flag anyone (fixed)

`AntiCheatScheduler` runs eight detectors every 60 seconds, and each one gates its
enforcement on `suspicionScore >= 75`. That score comes from `getCheatSuspicionScores()`,
whose backing map has exactly one writer: `AntiCheatEngine.detectCheating(board, user)`.
That method had exactly one caller — `EventEngine.submitEventScore` — **which has no
callers of its own anywhere in the codebase**. No controller maps to it; no service invokes
it. Confirmed by a repo-wide search: the only occurrence of the name is its own
declaration.

So the map was permanently empty, all eight detectors compared `0.0 >= 75` once a minute
and took the else branch, and no player could be flagged for anything regardless of
behaviour. Nothing errored. The scheduler paged up to 500 boards and queried the user table
every cycle to reach a decision it was structurally incapable of making, and the
`sudokupro.suspicious.players` gauge read a flat zero — so the dashboard actively confirmed
the system was healthy.

Two of the eight detectors were dead a second time over: IP-clustering reads
`ipSolveCounts` and device-switch reads `deviceSwitches`, and nothing wrote either.
`detectCheating` computed the player's `ip` and `platform` into local variables and then
discarded both.

Fixed by adding `AntiCheatEngine.scoreCompletedGame(board, playerId)` — which resolves the
`User` itself, so GameService's dependency graph is unchanged — and calling it from
`GameService.applyMove` at the point a board is actually solved; and by recording the ip
and platform that were already being computed. Enforcement policy is deliberately
unchanged: the existing immediate flag for impossible solve times still fires, and the
threshold-75 decision still belongs to the scheduler. This pass makes the input real, it
does not make the punishment harsher.

### P1 — `solveTime` read as zero on every board loaded from the database or Redis (fixed)

`solveTime` is a `@Transient` `Duration`; only the derived `solveTimeSeconds` column is
persisted, and nothing rebuilt the Duration on the way back in. `getSolveTime()` therefore
answered `Duration.ZERO` for every rehydrated board no matter how long the player took.

This is what made the anti-cheat fix above dangerous to ship on its own. `detectCheating`
scored "solved impossibly fast" against a rehydrated board — `0 < difficulty * 10s` is
always true — and stacked a second signal for "under 500ms per move" on the same zero. With
the pipeline newly live, that would have manufactured suspicion out of a serialization
artefact rather than behaviour. Two other consumers were wrong for the same reason:
`EventEngine.calculateEventScore` subtracts a time penalty of `solveTime / 10`, so a slow
solve replayed after a cache miss scored strictly **higher** than the identical solve served
from memory; and the solve-time analytics recorded zero seconds for those games.

Fixed at the root — `@PostLoad` and a Jackson setter both restore the Duration from the
column — and defensively, by guarding both zero-elapsed-time signals in the detector.

### P2 — `sudokupro.active.users` measured uptime, not users (fixed)

A Micrometer **Counter** incremented *by the absolute head-count* every cycle. A steady 40
active users reported 40, then 80, then 120: the series measured how long the pod had been
running, and any `rate()` over it was noise. "Users active in the last 24h" is a level, so
it is now a gauge.

### P2 — `sudokupro.solve.time.average` was not an average solve time (fixed)

`solveTimes` holds a *cumulative* sum of seconds per player, and `getAverageSolveTime()`
averaged that map's values — so each sample was one player's lifetime total rather than one
solve, and the figure climbed without bound as regulars kept playing. A player who had
finished forty puzzles contributed forty puzzles' worth of seconds as a single data point.
Now divides summed seconds by a summed solve count.

### P2 — ChaosEngine leaked five map entries per player, forever (fixed)

`playerLuck`, `playerProfiles`, `playerKarma`, `playerBrainprints` and
`universeSignatures` are keyed by player and were only ever cleared by `resetPlayerState`,
which runs on the "RESET" event alone. Meanwhile `GameService.applyMove` fires
`onGameEvent("MOVE", playerId)` on *every move*, and that path writes `playerLuck` and
creates a `LuckProfile`. Heap grew with lifetime unique players and was released only by a
restart, for transient flavour state nothing needs past a session. Now a bounded LRU
(10,000 players) that evicts a player from all five maps together.

Also removed `cosmicConsistency` and `movePatterns` from `AntiCheatEngine`: neither was
ever written or read: they were declared, trimmed on every observation, and nothing else.

### Harnesses now run in CI

`.github/workflows/ci.yml` gains a `harness` job, and the release job now waits on it. The
JUnit suite cannot reach what these three do, and the audit history shows it: the
nested-lock stall, the WebSocket move-parsing break, the `/solve` ownership hole and the
`/end` replay farm all had green unit tests over them and were found by the harnesses.
Running them only by hand meant a regression could land on main unnoticed.

The job brings up Postgres 16 and Redis 7 as service containers, runs the engine's 26
invariants against the real model, boots the server jar under the **dev** profile — the
`test` profile disables `SecurityConfig` outright and would turn every authorization
assertion green for the wrong reason — waits on `/actuator/health`, then runs both Python
suites. All three previously printed their failures and exited 0; each now exits non-zero
on a failed check, so a regression fails the build instead of scrolling past in a green log.
The whole sequence was executed end to end before being committed: engine 26/26, adversarial
27/27, fuzz 28/28.

### Still open (deliberately not changed)

- **`flagPlayer` is close to cosmetic.** It halves the player's `cosmicDrip` and increments
  an in-memory counter that a restart clears; `endGame` still pays a flagged player in full.
  Making flags durable and withholding rewards is a product decision about false positives
  on heuristic detectors, not a bug fix, so it needs your call rather than mine.
- **`@EnableCaching` is absent repo-wide**, so every `@Cacheable` annotation is inert. Left
  alone on purpose: switching it on would silently introduce staleness across paths that
  have never run with a cache.
- **The leaderboard query pairs `@EntityGraph` with `Pageable`**, which makes Hibernate
  paginate the whole users table in memory. Fine at current scale, wrong shape at growth.

## HARDENING PASS 9 — 2026-07-25 (deep audit: HTTP layer, competitive, persistence, front end)

Suite **243 → 254 tests**; adversarial suite **27 → 41 checks**, all passing; fuzz 28/28;
engine 26 invariants / 0 bugs. Four independent audits — controllers/DTOs, duel/daily/
leaderboard, persistence/concurrency, and the web client — each asked to substantiate every

### P0 — unlimited gem minting via `POST /api/game/import` → `POST /{id}/end` (fixed)

The share code is attacker-authored: unsigned, unauthenticated, never checked against
anything the server issued. `restoreCells` validates only *shape*, so a fully completed grid
with every cell marked `"ms":"PLAYER"` imported cleanly. `isSolved()` is computed from the
grid rather than stored, so the board was solved the instant it existed, and `/end` paid out
in full — **every reward guard from the previous eight passes was bypassed at once, from a
direction none of them faced**: the caller genuinely owns the board so the ownership check
passes; `hasAutosolvedCells()` finds no AUTOSOLVE source because the attacker wrote PLAYER;
and the `rewardsGranted` replay guard never fires because each import mints a fresh
`shared-<uuid>` id.

Measured live: **15 → 140 gems in five request pairs.** No race, no timing, no second player.

An import now yields the *puzzle*, not the sender's progress — every non-given cell is
cleared, so 81 non-given values import as an empty board — and a grid claiming more than 64
clues is refused outright (a 9×9 with a unique solution needs at least 17, so at most 64
givens), which blocks the obvious follow-up of marking all 81 cells `"g":true`. Decompression
is bounded at 64KB: the 16KB cap on the *encoded* field said nothing about the decompressed
size, and gzip reaches ~1000:1, so 12KB of body expanded to ~12MB of String plus a multiple
of that to parse — fifty concurrent requests OOM'd a single-replica pod. Re-verified live:
four import+end cycles now move the wallet by zero.

### P0 — `GET /api/game/{gameId}` had no ownership check (fixed)

Pass 4 hardened the WebSocket layer against exactly this: `isSharedPuzzle` closes the
spectate channel for the `daily-`/`week-`/`duel-` prefixes, and its comment records a
verified exploit where an attacker watched a victim's 53/81 daily board. **The REST read was
never given the equivalent check**, so one `GET /api/game/daily-<date>:<victim>` bypassed the
whole mitigation and returned all 81 cells. Competitive ids are deterministic and usernames
are public from the leaderboards and the duel list, so the id is trivially constructible.

Duel boards make it worse than surveillance: both players race copies of the *same* puzzle,
so every value the opponent has entered is a correct answer to copy, pollable in real time.
Verified live — the attacker read the victim's 33/81 daily board; now 403.

`GET /{gameId}/share` was a second, independent path to the same data (finding P1 below), and
`GET /api/game/active-of/{playerId}` is a discovery aid for both. The predicate now lives in
`GameService.isCompetitiveGameId` and `WebSocketController.isSharedPuzzle` delegates to it,
so the two guards cannot drift apart again.

### P0 — `users.username` had no uniqueness at any layer (fixed, Flyway V9)

No `@Column(unique = true)`, nothing in the baseline schema, and no lock around the several
check-then-insert callers. `EconomyService.walletFor` is the worst: two hint requests from
one brand-new player on two different games take two *different* per-game locks, so both miss
the lookup and both insert.

This is the same bug class V8 fixed for `game_id`, with a much larger blast radius.
`findByUsername` is a single-result query, so from the moment a duplicate exists it throws
`IncorrectResultSizeDataAccessException` on every call — not an `IllegalArgumentException`,
so no caller's catch block handles it. Every hint, every payout, every friend request naming
the player, and `loadUserByUsername` all 500 permanently: **the player cannot log in**, and it
does not heal on restart.

V9 dedupes (keeping the row that can authenticate, then the one with the most progress) and
adds a partial unique index. `walletFor` now provisions with `saveAndFlush` so the loser of a
race sees the constraint fire inside its own try/catch and re-reads the winner's row, instead
of turning silent corruption into a 500.

### P1 — the one Redis read with no fallback (fixed)

Every other Redis touch in the codebase degrades — `saveToRedis`, `acquireRedis`, all four
state stores, the broadcast relay. `GameService.getGame`'s cache read did not, so a
connection failure, a timeout past the 2s budget, or one poisoned entry propagated instead of
falling through to the database row sitting right behind it. The controller catches only
`IllegalArgumentException`, so it surfaced as a 500 — and Redis was still technically *up*, so
readiness passed and the pod kept serving 500s for reads, moves, hints, saves and ends.

### P1 — FREEZE could target any player on the platform (fixed)

`PowerUpService.use` checked only "not blank, not me" before locking the target's input for
ten seconds. The class javadoc says FREEZE "locks a **duel opponent's** input" and its two
siblings both go through `requireOwnGame`; this had nothing. Pick a name off the public
leaderboard and grief them. It is silent to the victim too: `applyMove` drops a locked
player's move with a log line and no error, while the WebSocket layer has already broadcast
the move envelope — so their client shows a move the authoritative board never recorded.
Verified live against an unrelated account. Now requires an ACTIVE duel between the two.

### P1 — Elo was not conserved at the rating floor (fixed)

An earlier pass listed "ELO math is symmetric" as verified-sound. True of `recordResult` read
in isolation, false in practice: `User.setDuelRating` clamps with `Math.max(0, ...)`, so once
the loser fell below the delta the winner still gained the full amount while the loser
surrendered less. Worked example at K=32 — winner 195 vs loser 5 gives delta 8, so the loser
drops 5 and **three points appear from nowhere**; from there every duel against the floored
account is +8/−0, up to roughly 720 points before the transfer saturates. The delta is now
capped at what the loser actually holds, so the exchange stays zero-sum at the floor.

### P2 — a batch of smaller correctness fixes

- **`KEYS` on the request path.** `GET /api/tournament/standings` ran `redis.keys(pattern)`,

  Now `SCAN`.
- **The daily archive silently truncated.** Weekly templates share `TEMPLATE_PLAYER`, and

- **Missing tie-breakers.** `findDuelLadder` and the three leaderboard queries ordered by one
  column only, leaving ties in an order Postgres does not guarantee between executions. The

- **The hint path never persisted its own charge.** `getHint` was the only mutating method in

  the `hintCount` it paid for lived only in the pod's memory, so an eviction or restart before

- **`/api/game/hint` returned 500 for an unknown or busy game**, echoing the internal message,

- **`DELETE /api/friends/{playerId}` was a row factory.** It called `walletFor` on an

## HARDENING PASS 10 — 2026-07-25 (generation, solver, auth wiring, realtime)

Suite **254 → 262**; engine **26 → 27 invariants**, 0 bugs; adversarial 41/41; fuzz 28/28.
Two audits over the subsystems no previous pass had read in depth — auth/security/deployment

**Two of the P0s below are failures of earlier fixes in this very document.** That is the

### P0 — every regular game was still one grid, relabelled (fixed)

Pass 1 recorded GEN-DETERMINISTIC-SOLUTION: a fixed candidate order made the backtracker
deterministic, so every board had the same solution. The fix drew a shuffled 1..9 permutation
and passed it to `solve(...)`. **That only renamed the digits.** One permutation reused at
every cell leaves the search path identical, so the structure never changed: 40 boards across
all five difficulties canonicalise (relabel row 0 to 1..9) to **a single grid**. Nine clues,
one per digit, pin the permutation and hand over the entire solution with no solving at all —
which defeats the hint economy, clean-solve bonuses, achievements, streaks and the anti-cheat
move model in one step.

The engine harness passed throughout, and that is the second half of the finding: its
diversity check compared completed grids **literally**, and relabelled grids differ literally.
A test that cannot fail is worse than no test, because it is cited as evidence. The harness
now canonicalises before comparing (new suite T1b) and would have caught the original bug and
the bad fix. Verified: **1/30 distinct canonical grids before, 30/30 after.**

`SudokuGenerator.solveSudoku` reshuffles per cell and always did, which is why daily, duel and
tournament boards were never affected — only the `new SudokuBoard(difficulty, ...)` path that
`GameService.createNewGame` uses, i.e. every ordinary game.

### P0 — SecretsGuard has never run, in any deployment (fixed)

`SudokuProApplication.optimizeStartup` calls `app.setLazyInitialization(true)`, and Boot's
lazy sweep exempts only `SmartInitializingSingleton`. `SecretsGuard` is a plain `@Component`
that nothing injects and nothing fetches — so it was never instantiated and
`afterPropertiesSet()` never fired. **The entire fail-fast credential check has been dead
since the day it was written**, and every pass since has cited it as the mitigation for
AUDIT P0-2.

Verified by booting the real jar under the prod profile with `DB_PASSWORD=sudoku123` and
`ADMIN_PASSWORD=secret` — the exact defaults still shipped in `application-dev.properties`,
and the exact values the guard exists to reject. It started cleanly and `/admin/constants`
answered 200 to `admin:secret`. Adding `--spring.main.lazy-initialization=false` to the same
command made it refuse, which isolates the cause.

Neither test level could catch it: `SecretsGuardTest` constructs the class by hand, and
`@SpringBootTest` never goes through `SudokuProApplication.start()`, so lazy initialization is
never applied in CI. The guard now implements `SmartInitializingSingleton`. Re-verified on a
clean database: default credentials → `Refusing to start: DB_PASSWORD ... well-known default`,
exit 1; real credentials → `credential checks passed`, health 200.

Related and fixed alongside: `main()` caught startup failure and called `shutdown()`, which
ended in `System.exit(0)`. A deployment that correctly refused to start reported **success**
to the orchestrator, so it was never crash-looped and the error never surfaced.

### P1 — hints were guesses, and REVEAL_CELL wrote them into the board (fixed)

`collectAllHints` emitted `candidates.get(0)` — the smallest locally legal digit — for any
cell that was not a naked single, and sold it as "Try placing N at row R, col C" for 5 gems.
Over 25 boards with no naked single available, **16 of those hints named a digit that was not
the answer**.

The damaging half is `REVEAL_CELL`: it runs the same ranking and **writes the value into the
board**. A wrong-but-legal digit is accepted, and on difficulty-4 and -5 boards every wrong
reveal rendered the puzzle **unsolvable**. The player spent a purchased item to have their
game silently destroyed, and was charged a hint against their clean-solve bonus for it. The
solver now completes the grid once and reads the true value out of the solution, so every
hint is correct by construction; an inconsistent position yields no hint rather than a
confident guess the player pays for.

### P1 — hint quality degraded with server uptime (fixed)

`cosmicHotspots` is keyed by coordinate only — no game, no player — so it is one global map
shared by every board in the JVM. Every issued hint added 2, only `solveSudoku` decayed it,
and the bonus was uncapped, so after roughly 23 hints ever taken at a coordinate it overtook
the 90-point gap between a naked single and a mere candidate. Measured with one long-lived
solver and a fresh board per request: clean to request 40, then a steadily rising share of
non-deducible hints — quality decaying purely as a function of uptime, resetting only on
restart. The boost is now capped and the map bounded.

### P1 — the brute-force lockout was bypassable, and the client IP was spoofable (fixed)

The counter was keyed on remote address alone, and `recordSuccess` deletes the key — so a
success from **any** account cleared it. Registration is permitAll and CSRF-exempt, so an
attacker registers their own account, guesses four passwords, logs in once as themselves, and
repeats. Measured: twelve consecutive wrong-password attempts against one target, zero 429s,
where the control run produced a 429 on the sixth. The counter is now scoped to
(address, account).

Separately, `server.forward-headers-strategy` defaulted to `NATIVE`, and the comment above it
argued that Tomcat only honours `X-Forwarded-For` from a private-range peer so it cannot be
spoofed. **In Kubernetes the peer is always private** (pod/node IP via kube-proxy), and the
shipped manifests contain only a ClusterIP Service with no ingress appending a real client
address — so the header was attacker-controlled end to end. That gave unlimited
unauthenticated guessing by rotating the header (verified: 12 attempts, no 429) *and* a
targeted denial of service: five bad logins stamped with a victim's egress IP locked that IP
out of the whole API, since the filter returns 429 before authentication so even correct
credentials fail. Now defaults to `NONE`; set `NATIVE` only behind a proxy that genuinely
appends the client address.

### P1 — a concurrent join and leave permanently muted the joining player (fixed)

`unregister` did `sessions.remove(session)` then a separate `if (sessions.isEmpty())
gameSessions.remove(gameId)`. A `register` landing on that Set in between left the new session
inside a Set no longer referenced by the map: the socket was open and the player believed they
had joined, but no broadcast could reach them — no moves, no chat, no board syncs, no leave
events — for the rest of the connection, with no recovery. Reproduced under contention: 5 of
25,621 broadcasts missed a live registered session. The emptiness test and the removal are now
one atomic `computeIfPresent`, and `register` retries if its Set was orphaned.

### P1 — the gem lost-update, closed on the reward side too (fixed)

`deductGemsIfAffordable` exists because read-modify-write on `gems` loses updates, but the
reward path still did `setGems(getGems() + earned)` + `save(wallet)`, which flushes a full-row
UPDATE from a snapshot read earlier in the transaction. A concurrent hint charge committing in
between was silently reverted — 15 gems, a payout computing 45 from the stale read, a charge
taking the balance to 10, then the payout writing 45, and the hint came out free. Solve
rewards now credit atomically in SQL, and `PowerUpService.buy` charges through the same
conditional UPDATE a hint uses (it had the same read-modify-write, so two concurrent buys both
saw the same starting balance).

### P2 — a batch of correctness and hygiene fixes

- **A rejected move was still broadcast.** `GameService.applyMove` returned void, so the
  WebSocket handler had no success signal and announced every move — including ones dropped
  silently for a FREEZE-locked player, leaving every client holding a value the authoritative
  board never recorded, with nothing to trigger a resync. It now reports whether the board
  changed.
- **Every move fanned out twice**, once from `SudokuBoard.applyMove` through
  `MultiplayerBroadcaster` and again from the handler — two envelopes per peer and two Redis
  publishes per move. The service-level broadcast is kept (it reaches every replica and covers
  REST-initiated moves); the duplicate is gone.
- **`SecureRandomGenerator.methodLog`** was a `Collections.synchronizedList` that every method
  appended to, never read, never cleared, with no getter. It grew at ~208 entries per generated
  board plus one per player move, forever, and serialised every RNG call from every request
  thread on one monitor. Removed.
- **Three native queries referenced a `match_history` table that does not exist** (the real one
  is `user_match_history`, with `match_won`/`match_timestamp`). Native queries are not validated
  at bootstrap and none has a caller, so nothing failed today — they would have thrown on first
  use. Corrected.

### Still open (deliberately not changed)

- **Cross-replica staleness in `activeGames`** — carried forward from pass 9. The read-through
  only runs on a miss and nothing invalidates the entry, so at `replicas > 1` a pod can serve a
  stale board and persist it over a newer row. Still a design decision (invalidate on write via
  the existing pub/sub relay, or make the cache write-through) rather than a patch.
- **`sudokupro.ws.allowed-origins` defaults to `http://localhost:8080`** and is set nowhere in
  the properties, compose file or manifests. It fails closed, so it is not a hole — but it means
  the WebSocket handshake returns 403 in any deployment that is not literally localhost:8080,
  i.e. **multiplayer is broken in production as shipped**. Left alone because the correct value
  is your deployment's real origin, which I do not know.
- **`GET /api/game/hint` mutates state on a GET**, so it is CSRF-exempt by design and reachable
  on the session cookie alone; a drive-by page can drain a victim's gems 5 at a time and bump
  their hintCount. It should be a POST, which is a breaking API change for the desktop client.
- **`POST /api/auth/register` is unthrottled** — BCrypt at ~110ms a call against a 1-CPU pod, an
  unbounded row-creation path, and a 409/201 account-existence oracle.
- **The web client's Log out never calls `POST /logout`**, so the server session stays valid
  until the 30-minute idle timeout.
- **`chaosMode` and `mirrorMode` are no-ops in `SudokuGenerator`** (their predicates can never
  match), yet chaos still shortens the clock from 300s to 60s — a 5x harder timer with none of
  the promised effect. And `cosmicDripFactor > 0` always produces an unsolvable puzzle; latent
  today because nothing serves event boards to players.
- **`@Async` on `NotificationService` is inert** (no `@EnableAsync` anywhere), so push I/O runs
  synchronously inside the game lock — a slow FCM endpoint can stall game completion for ~20s.
- **`flagPlayer` is close to cosmetic**, `@EnableCaching` is still absent repo-wide, and the
  leaderboard `@EntityGraph` + `Pageable` still paginates in memory. Carried forward.

## HARDENING PASS 11 — 2026-07-25 (the engines: in-process 27 -> 40, and a new live engine)

Suite **262 → 270**; model engine **27 → 40 invariants**; and a new **live game-playing
engine at 111 invariants**, all green. Adversarial 41/41, fuzz 28/28.

The motivation is pass 10's headline finding: a generator bug survived a "fix" because the
in-process harness compared grids literally, and a credential guard was dead for its whole
life because no test ever booted the application. Both were blind spots of *kind*, not of
effort. `engine/Engine.java` drives model classes in-process — it never issues an HTTP
request, never opens a WebSocket, never touches Postgres or Redis, and never observes what
two players do to each other. Every P0 in this document involving authorization, the
economy, persistence or the realtime layer was invisible to it by construction.

### The live engine (`engine/live_engine.py`)

It registers real accounts, logs in, and **plays** — full games from an empty grid to a
solved board, over the same REST + WebSocket API the browser and desktop clients use (moves,
undo, redo and sync are WebSocket verbs; there is no REST move endpoint). It carries its own
Sudoku solver and uniqueness checker, deliberately independent of the server's, so the
server is graded against an outside opinion rather than its own.

Twenty-two suites, 111 invariants: puzzle quality (consistency, solvability, **uniqueness**,
and structural diversity after canonicalisation), full play to victory, payout-exactly-once,
illegal-move rejection, move-source spoofing, hint correctness against the unique solution,
undo/redo as exact inverses, save/resume and cache-eviction round-trips, cross-player
isolation, economy conservation under real concurrency, daily/duel privacy and rating
zero-sum, power-up buy/spend accounting, saved-game and leaderboard correctness, multi-session
visibility, mid-game reconnect, share/import round-trip, chaos and mirror modes, hostile
input, and a soak of 12 concurrent players playing 60 games to completion. Any 5xx anywhere
in the run is a finding on its own.

**It found three server bugs on its first full run.**

### P1 — chaos mode corrupted the board and could make a game unwinnable (fixed)

`triggerChaosSwap` swapped two arbitrary non-given cells **with no legality check**.
Swapping two different values across a Sudoku almost always creates a duplicate — moving a
5 into a row that already holds one — and the damage compounds: `isValidMove` then rejects
the player's own CORRECT moves, because the stray duplicate blocks the value that genuinely
belongs there. The player is left unable to finish a game they were playing correctly, with
nothing on screen explaining why.

A swap is now applied only if the board remains a legal Sudoku afterwards, sampled over a
bounded number of candidate pairs. Chaos still shuffles the player's entries; it no longer
corrupts the puzzle. Pinned by `ChaosSwapLegalityTest`, which hammers 40 boards with 25
chaos ticks each and asserts consistency, completability and given-clue immutability after
every one.

### P2 — difficulty 5 was unreachable and returned 500 (fixed)

`@Min(1) @Max(4)` on the controller parameter contradicted `GameService.validateDifficulty`,
`SudokuBoard.generateBoard` and `Constants`, which all document 1–5. So the platform's
hardest difficulty could not be requested at all — and asking for it raised a
`ConstraintViolationException`, which has no default Spring MVC mapping and escaped as a
**500 with an empty problem body** and a stack trace in the log. A client cannot tell "you
asked for something impossible" from "the server is broken", and a 500 is what monitoring
pages on. The bound is now 5, and an `@ExceptionHandler` maps every parameter-validation
failure to a 400 that names the offending parameter. The model engine confirms difficulty 5
is real: clue counts run d1=53.0, d2=46.0, d3=39.0, d4=32.0, **d5=25.4**.

### P2 — a coordinate of -1 passed validation and threw deep in the board (fixed)

`EnhancedMove`'s canonical constructor guarded `row < -1 || row > 8`. The lower bound was
off by one and -1 is not a sentinel anywhere in the codebase, so a move at row or column -1
passed the guard and then threw `ArrayIndexOutOfBoundsException` inside the board —
surfacing as a raw "Index -1 out of bounds for length 9" and logging an ERROR for what is
really a malformed request. Found by feeding out-of-range coordinates over the WebSocket.

### The model engine grew from 27 to 40 invariants

Nine new suites, aimed at the classes of bug the previous set could not express: unique
solutions across every difficulty (not just solvable ones); difficulty actually changing the
clue count monotonically; generated boards never served already inconsistent; a rejected
move leaving both the grid AND `moveCount` untouched (an inflated count corrupts the
analytics the difficulty model and the anti-cheat detectors both read); counters surviving a
snapshot round-trip; the same puzzle always resolving to the same answer; a solved board
staying sealed against further input; twelve boards played interleaved staying independent
(a single shared mutable field in the model would show up here and nowhere else); and the
replay history reproducing exactly the moves played.

### Two false positives, and why they are worth recording

The live engine's first run also reported a redo failure and a power-up accounting failure.
Both were **the harness's fault**: `simple()` read a stale board broadcast left in the socket
buffer by the previous verb, and the power-up suite polled an endpoint that does not exist
(inventory is nested under `GET /api/powerups`). Both were confirmed against the running
server before any code was touched, and the harness was fixed instead. A bug-finding tool
that cries wolf is worse than one that misses, because its green runs stop meaning anything —
the same failure mode as the literal-comparison diversity check in pass 10.

### CI

`.github/workflows/ci.yml` now runs four harnesses on every push: the model engine, the
adversarial suite, the **live engine** (8 players x 3 games), and the fuzz suite — against
Postgres 16 and Redis 7 service containers. All four exit non-zero on failure.

## HARDENING PASS 13 — 2026-07-26 (the simulator at scale, the untested half, the front end)

Suite **291 → 550**. Live engine **145 → 149** invariants. Three strands: the live simulator
grew fault injection and found a P1 nobody's unit tests could see; five parallel audits took
the never-tested classes from zero coverage to 250 mutation-verified tests; and the web

**The theme of this pass is code that was written correctly and never connected.** Three
separate findings have that identical shape, and it is now the third pass in a row where the
defect was not bad logic but unreachable logic.

### The simulator's finding: "degrades gracefully without Redis" was false

`engine/live_engine.py --only L28 --fault-injection` stops Redis mid-session and keeps
playing. Boards stayed readable and new games could still be created, but **a full game
could not be played to completion**. The server log gave the reason, once per move:

```
10:40:34.257 WARN GameService : Redis cache write failed for game 208e00e3 (non-fatal): Redis command timed out
10:40:44.265 WARN GameService : Redis cache write failed for game 208e00e3 (non-fatal): Redis command timed out
```

Ten seconds per move. Every Redis touch in this codebase is already wrapped in a try/catch
with a local fallback, and the design notes call the service gracefully degrading without
Redis — but Lettuce's default `DisconnectedBehavior` **queues** commands while disconnected,
hoping for a reconnect, so the catch never ran until the command timeout expired. *The
fallback was correct and unreachable.* Worse than slow: each queued move holds a request
thread, so a Redis blip escalates from a cache miss into thread-pool exhaustion.

`spring.data.redis.timeout=2000ms` was already set and did not help — it is not applied as a
Lettuce `TimeoutOptions` fixed timeout for commands issued while the connection is down.

Fixed by `RedisFailFastConfig`: `REJECT_COMMANDS`, a 500ms command and connect timeout, and
`cancelCommandsOnReconnectFailure`, with `autoReconnect` retained so one Redis restart is not
permanent. L28 now passes all seven checks including *"a full game plays to completion with
Redis down"* and *"the board is readable again after Redis recovers."*

**Why no unit test could have caught this.** Every test exercising the Redis fallbacks mocks
the template to throw *immediately* — that is, they all assumed exactly the behaviour this
config finally makes true. The mocks were not wrong about the desired semantics; they were
wrong that the semantics existed.

### Two more never-connected paths, both surfaced by the front-end pass

- **P1 · The WebSocket handshake never percent-decoded `?gameId=`.** Daily and duel ids embed
  a player name after a colon (`daily-2026-07-26:someuser`), the web client builds its URL

- **P2 · `MultiplayerBroadcaster.broadcastHealthPing()` had no caller.** A repository-wide

  `readyState === OPEN` and fires no event, left clients sitting on a dead connection
  believing they were live (measured at >20s in a real browser). Now `@Scheduled`, with the

`HealthPingWiringTest` asserts the annotation itself rather than the envelope, deliberately:

## HARDENING PASS 15 — 2026-07-26 (the last known-open item, and the harness that stopped running)

Suite **719 → 729** (609 server + 120 client). Every item on pass 14's known-open list is now
either fixed or deleted. The pass also found something nobody was looking for: **pass 14's own
registration throttle had been quietly starving two of the three CI harnesses since the day it
shipped**, and the harness that was supposed to notice announced a skip instead.

### The cross-replica cache, which five passes had left alone

`activeGames` is documented as a read-through cache with the authoritative copy in Redis/DB, and
`getGame` trusted a cache hit **forever** — there was no TTL, no version check, no comparison
against the Redis copy. Once a board entered a pod's map, that pod served and *mutated* its own
copy until eviction.

The failure is not a stale read. It is a **lost update under the lock**: pod A takes the game lock,
applies a move, writes Redis and the database, releases. Pod B then takes the same lock, cache-hits
its pre-move copy, and applies a move to a grid that no longer exists. `GameLockManager` serialises
the mutations and says nothing about the cached copies, so the mutual exclusion everyone reasons
about is real and the data race survives it anyway. `shutdown()` already carried a comment
describing the read-only half of this hazard (`locallyMutated` exists precisely so a pod does not
flush boards it merely looked at) — the write half was never addressed.

Fixed with a per-game version counter in Redis. Every write bumps `game:ver:<id>` **after** the
board write, so a replica that observes a new version always finds the new board behind it; every
cache hit validates against it before being trusted, and a mismatch drops the copy (and its
`locallyMutated` flag, so the stale board cannot be flushed over the winner at shutdown) and falls
through to the existing read-through path. Both the bump and the check happen inside the per-game
lock, which is what makes this race-free rather than best-effort. Redis unreachable → validation
degrades to trusting the cache, matching what `GameLockManager` already declares itself to be in
that state: a single-replica deployment.

`GameServiceCacheCoherenceTest` runs two `GameService` instances over one simulated Redis and one
simulated database, with boards crossing between them through a real Jackson round-trip so each pod
holds a genuinely distinct object graph. It asserts the reload, that a pod's *own* writes do not
invalidate its own cache, and the Redis-down degradation. The stale instance is kept and asserted
against — the test proves the old copy really was stale, so it cannot pass for the wrong reason.

### Two dead analytics maps, and the metric that read 0.0 for it

`AnalyticsService.recordEvent` has dispatched on `"DUEL_WIN"`, `"DUEL_LOSS"` and `"STREAK_UPDATE"`
since it was written, against a `GameEvent.EventType` enum that has never contained them. Pass 12
diagnosed this correctly and removed the unreachable terms from the skill formula; pass 14 recorded
the consequence for `sudokupro.duel.win.rate.average` and left it. So the gauge published 0.0
forever, and `AntiCheatEngine`'s duel-win cross-check compared a persisted count against a map that
could never match it — a detector that could not fire, which is the same defect class as the theme
gauge and the skill stub.

The enum gained the three constants, and — the part that the previous diagnosis missed — an emitter
was added at each of the two sites that actually know the outcome. `DuelService.recordResult` wrote
`setDuelWins(...)` straight to the entity and told analytics nothing; `GameService` advanced streaks
the same way. Adding the constants alone would have fixed nothing. The skill formula deliberately
still excludes these maps, now on the surviving ground rather than the unreachability one: duel
skill is already served by the persisted ladder, and blending it in would double-count duellists.

### "No moves" was a hint the player paid five gems for

`AISolverService.getNextLogicalMove` returns the literal `"No moves"` when no logical move exists.
`purchaseHint` guarded the charge with `!hint.isBlank()`, which that string passes. So a player on a
position with no available hint was charged the full cost — and `incrementHintCount()` never runs on
that path, so the board recorded no hint in exchange. A charge with no purchase behind it, sitting
directly beneath a comment reading *"Empty hints are free."*

The sentinel is now a named constant the charge site compares against; the string itself is
unchanged, because `AISolverCorrectnessTest` pins it and clients display it. The no-move answer
still reaches the player, still free, and is still memoised so a replayed GET stays free.

### Two unlock paths, one reward, and a guard that refused its own keys

`AchievementService` wrote unlocks directly while `User.checkAchievement` paid 20 gems + 100 xp for

### The harness that stopped running, and said so quietly

harnesses against it from one address — and the adversarial suite needs about eight registration

Measured on the shipped jar: registrations 1-5 return 201, **6 onward return 429**. So the
adversarial suite died partway through with a `KeyError` on an error envelope it parsed as a board —
about twenty-five checks never ran, and the traceback did not contain the word "registration". The
live engine's later bots could not register at all. And `L32`, the suite that exists to prove the
throttle fires, reads the quota in force rather than assuming one and **skips when it is not told**:

the day it shipped.

This is pass 14's own doctrine — *a skip that looks like a pass is the defect* — one level up from
where it was applied. Three fixes: the harness instance gets a quota that lets the suites create

the counter starts clean) runs `L32` so the throttle is actually asserted rather than skipped; and
the adversarial suite now treats a throttled registration as a **fixture failure**, exiting non-zero
with the exact flag to set and an explicit statement that nothing below that point was verified.
Raising the quota to keep a harness quiet is what the L32 docstring warns against — the quota is
raised only where nothing tests it, and lowered where something does.

### The same defect twice: a completion scored against the clock instead of the puzzle

`DailyPuzzleService.onGameEnded` and `WeeklyTournamentService.onGameEnded` both recomputed the
current period at *solve* time and required it to match the id the board was stamped with at
*join* time. A puzzle carried across the boundary — joined 23:58, finished 00:01 — therefore
matched nothing and fell out with **no record and no log**: completion, streak, leaderboard entry
and notification all discarded, for the player's most impressive category of solve.

For the tournament it is worse than one lost result. Standings require all five puzzles, so a
single boundary crossing disqualifies the player for the entire week — and a Sunday-to-Monday
boundary is inside every tournament by construction.

Neither could be caught, because **every daily and weekly test pins a `Clock.fixed`** — the one
arrangement in which join time and solve time cannot disagree. The bug lived precisely in the gap
the tests defined away. `PeriodBoundaryCreditTest` therefore uses a *movable* clock and states in
its own javadoc that a fixed clock there would silently stop testing anything.

The date now comes from the board's id, which is the authoritative statement of which puzzle it
is; the clock only decides whether that puzzle is still current enough to score. Back-dating is
bounded to one day for the daily — the same window `DailyStateStore.getStreak` already calls a
streak "alive", and inside its 3-day key TTL, so a completion can neither land on a day the
streak model has written off nor resurrect an expired leaderboard — and to the previous week for
the tournament, whose times key lives 14 days. Anything older earns gems and says so in the log
instead of vanishing. Back-dating is safe for the leaderboard because the score is the board's
own elapsed timer: a straggler ranks by how long they took, not by when they finished.

**A second bug fell out of fixing the first.** `advanceStreak` had no ordering guard, so a
completion for an older day than the one already recorded fell through to its final `else` and
reset the streak to 1 *and moved `lastDate` backwards* — which then failed the aliveness check
too. Measured on the de-fixed code: a live 3-day streak reads **0**, not 1, and no later
completion can extend it. Filling in yesterday must never cost a player the streak they hold.

### A paid power-up that changed the board in one pod's memory and nowhere else

`PowerUpService` applied REVEAL_CELL through `applyExternalMove` — deliberately the
*non*-broadcasting variant — and then called neither `saveToRedis` nor `persistBoard`. Nothing
marked the game `locallyMutated` either, which is the flag `shutdown()` keys on, so even the
shutdown safety net skipped it. The player paid 20 gems; the digit lived in one replica's cache
until the next trim, restart, reconnect or cross-replica read dropped it — and after pass 15's
version check, the next write from *any* other replica drops the copy holding it outright. The
desktop client re-renders its stale local board, so there was nothing to see either. EXTRA_LIFE
had the same gap, and in infinite mode the life a player bought vanished before it could be spent.

Both now run through `GameService`, which is the one place that holds the game lock, broadcasts,
and writes through. The existing tests asserted *"a cell got filled"* — true throughout the bug's
life — so the new ones assert the plumbing instead: the write-through pair ran, and peers were
told.

### A first `/api/season` call mid-quarter destroyed the ladder

crowned a podium and soft-reset **every rated player's rating** — mid-quarter, with no season

compressed the ratings it was only asked to report on.

The existing test **enshrined it**: clock fixed mid-Q3, one `current()` call, assert a podium and
150 resets. A rollover now requires evidence that a season ended while this install was watching —
the previous season's marker. Stated trade-off rather than a hidden one: an install dormant for a
whole season skips one reset instead of crowning a podium for a season nobody played. A missed
reset is recoverable; a spurious one is not.

## HARDENING PASS 17 — 2026-07-27 (the untested client, and a bug only CI could see)

Suite **746** (626 server + 120 client) plus a new browser harness. This pass began as "give
`app.js` a test" and turned into something more useful: **the first bug in this project that
local runs could not reproduce at all, found only because CI was made to say what it knew.**

### Pass 16 went red on CI and green everywhere else

The `test` job failed on pass 16 and again on the commit after it, while `harness` stayed green.
It did not reproduce here under **JDK 17 or 21**, with CI's own `DB_*`/`REDIS_*` environment,
through `test`, `verify`, and `clean verify`, on a **2-core box** (the same width as a GitHub
runner), across half a dozen runs. The one new test that depends on a randomly generated board
was hammered over **400 fresh puzzles** with zero failures, eliminating it.

The blocker was not the bug, it was **the channel**. A failing job showed the outside world one
line — `Process completed with exit code 1` — and everything that named the test lived behind a
sign-in. The first attempt at fixing that wrote the surefire output into a **log group and the job
summary, both of which are also gated**, so the second red build said exactly what the first had.
`::error::` annotations, it turns out, render on the run page for anyone. Switching to those
produced the answer on the very next run:

```
GameSessionRegistryRaceTest.aRegisteredSessionAlwaysReceivesBroadcastsDespiteConcurrentChurn
1 of 3000 registered sessions were unreachable — the join was lost to an orphan Set
```

Worth stating plainly, because it cost two builds: **diagnostics that only a signed-in maintainer
can read are not diagnostics.** Prefer the channel that carries information out of the system.

### The bug: a join lost to an orphan Set

`GameSessionRegistry.register` added the session to the game's Set **outside** the map's per-key
lock and then re-checked `gameSessions.get(gameId) == sessions`, retrying on a mismatch. That is a
check-then-act, and `unregister` decides whether to drop the entry with `sessions.isEmpty()` —
emptiness on a `ConcurrentHashMap`-backed Set is weakly consistent and can report empty while a
concurrent `add` from another thread is still in flight. So the sequence *A adds itself → A's
identity check passes → B removes the entry it just observed as empty* leaves A holding an open,
apparently-registered socket inside a Set nothing can reach. A never retries: its check already
succeeded.

For the player the failure is total and silent. The socket is open and the client believes it
joined, but `deliverToGameLocal` finds no entry, so they receive no moves, no chat, no board syncs
and no leave events for the rest of the connection — and never recover, because a later join
creates a different Set. The trigger is ordinary: one player leaving a game as another joins it.

The `add` now happens inside `compute()`, which holds the same per-key lock `unregister`'s
`computeIfPresent` takes, so the two cannot interleave and the orphan outcome is impossible by
construction rather than detected and retried. The retry loop is gone. Reproduced locally at
**5 in 120,000**; **0 in 480,000** after the change, then green on CI.

Note the shape: an earlier pass had already fixed the *unregister* half of this race and left a
retry loop guarding the *register* half. A retry that guards a check-then-act is not a fix, it is
a narrower window.

### The web client had no test of any kind — and the first version of its harness proved nothing

`testing/web_client_test.py` drives real Chromium against a real server and **plays a whole puzzle
through the UI**, then asserts what the player experiences: the win is announced, the solve time
is shown, pencil marks survive a dropped-and-restored connection, and no uncaught JS error
occurred. Playing for real is the point — the solved-game detection only happens when a final move
genuinely lands.

**Its first mutation audit came back 15/15 green against a deliberately broken client.** Spring
serves `/play/app.js` out of the packaged jar, so edits to the source tree never reached the
browser: the harness was faithfully testing a client nobody was editing. Serving the static files
from disk exposed it, and the real audit then found a second problem — neutering `onSolved()`
failed "the player is told they won" and "the solve time is shown" but **not** the check asserting
the solved CSS class, because `case 'board'` toggles that class *before* it calls `onSolved`. That
check's message claimed more than it proved, so it was split in two and reworded. A separate
mutation making a resync discard notes failed the pencil-mark check, as it should.

Both defects were in the *safety net*, not the product. That is the failure mode this project
keeps finding, and this time it was in the thing built to prevent it.

invocation and read back the scheduler's rather than its own). Two flakes from one pattern is the
pattern's verdict, so the mock is now a plain recording double with no stubbing phase to race.

## HARDENING PASSES 18-21 — 2026-07-27 (features that were never doing anything)

Suite **746 → 756** (632 server + 124 client). Four passes with one theme, which only became
visible once they were side by side: **three of the four fixed code that ran, logged, and
returned normally while accomplishing nothing.** Not crashes, not wrong answers — no answers.

That is a harder class to find than a bug, because every signal a team normally relies on says
the code is fine. It compiles, it is covered by a passing test, it appears in the logs, and the
feature it belongs to is shipped and toggleable in the UI. What is missing is any effect. Each
of the three below was caught the same way: by measuring the outcome instead of reading the code.

### Pass 18 — the desktop UI package had no tests, and that is where a P1 had lived

`client/` has seventeen test classes and every one of them was `net/` or pure logic. The **`ui`
package** had one (theme resolution) and nothing for `BoardView` — the class where
`setEditable(value == 0)` locked every filled cell as though it were a clue.

Worth restating why that bug survived so long: on a fresh puzzle it is *indistinguishable from
correct*, because the only filled cells are the clues. It appears only when a board is rebuilt
with the player's own work in it — resume, duel rejoin, daily join — and then the player gets
their game back with every cell they have already filled frozen, including the ones they filled
wrongly. Unfinishable, and invisible to any amount of manual play on a new game.

Four tests, reading the real scene graph rather than the private `cellFields` array. Mutation-audited
**one defect at a time**, which mattered: reverting both the `createCell` and `refreshCell` fixes
together made the refresh test fail on its *setup* line, proving nothing about itself. Isolated,
each fails on its own assertion.

Infrastructure note: JavaFX 21's public artifacts do not ship Monocle, so the usual
`-Dglass.platform=Monocle` headless route dies with a null `PlatformFactory`. CI runs the build
under `xvfb-run`; a developer with a desktop needs nothing. When the toolkit cannot start the
tests **fail** with that explanation rather than skipping.

### Pass 19 — a game mode that could never fire

`applyChaosTwist` looked for pairs of cells that were non-empty **and** non-given. No such cell
can exist when it runs: `markAllGiven` marks every cell, and `removeNumbers` only ever produces
`(value 0, given false)` — because `SudokuCell.setValue` refuses to clear a given, which is why
removal calls `setGiven(false)` first. The predicate is the empty set.

Measured before removal: **60 chaos boards, 0 swaps logged, 0 qualifying cells anywhere.** Every
chaos game burned the full attempt budget and logged a warning about failing to complete its
swaps.

It could not be repaired in place, either, and that is the more useful observation: at generation
time the only filled cells are the clues, and swapping two clues destroys the unique solution.
Chaos on the *player's* entries is the coherent version, and it already existed at play time in
`GameService.triggerChaosSwap`. So the mode was never broken — one of its two implementations was
incoherent by construction.

Replaced with the invariant that made it impossible, which is worth having on its own: **every
filled cell on a generated board is a clue.** A filled non-given cell is a leaked solution digit —
invisible in the UI, and free progress in a duel or daily where everyone races the same grid.

**Found while writing that test:** the generator's `seed` parameter does not make generation
reproducible. The RNG is a `SecureRandom`, whose `setSeed` *supplements* entropy rather than
replacing it. The first draft of the test assumed otherwise and failed. Nothing in production
depends on it, and the retry loop actually depends on retries *not* being replays — so it is now
documented on `generate()` rather than changed. Recorded because it is an easy assumption to make;
this pass made it.

Also cleared the Node 20 deprecation warning on every CI job (checkout v4→v6, setup-java v4→v5,
setup-python v5→v6, upload-artifact v4→v7).

### Pass 20 — a game mode that fired and changed nothing

Mirror mode was the same defect one level subtler: not dead, but ineffective.
`applyMirrorSymmetry` ran **after** `removeNumbers` — after the unique solution had been
established — and copied one half of the finished grid onto the other. Two guards from an earlier
pass (never blank a clue, never write a value that breaks the grid) are what kept it from
destroying the puzzle, and are also exactly what made it pointless: after removal, mirroring
almost always either blanks a clue or duplicates a digit.

Measured over 40 mirror boards: **~13 cells "mirrored" per board, the empty-cell count changed on
zero of them, and zero came out symmetric.** The writes that survived the guards were assignments
of a value the cell already held. The only observable effect was a burst of WARN lines per game.

A symmetric puzzle has to be *built* that way — removing clues in pairs with the uniqueness check
applied per pair — which `removeNumbers` already did under `enforceSymmetry`. Mirror now routes
there: **25/25 symmetric at EASY, MEDIUM and HARD**, exact clue counts, no failures.

Two guards on that, both measured. The removal target must be **even**, since pairs move the count
two at a time — NIGHTMARE asks for 55 and pair-wise removal overshoots to 56, shipping a board
whose clue count contradicts its tier (25/tier: EASY/MEDIUM/HARD 25/25 exact, EXTREME 24/25,
NIGHTMARE 6/25 and all six off-target). And the final retry drops symmetry, because a symmetric
layout is a preference while a playable puzzle is not.

Checked before changing anything: mirror boards were never actually broken — 40 boards, all
uniquely solvable, before and after.

### Pass 21 — a detector that could never fire

The duel-win check required an in-memory counter to be **exactly equal** to a persisted one:

```java
duelWins > MAX_DUEL_WIN_STREAK
  && analyticsService.getDuelWins().getOrDefault(playerId, 0) == duelWins
```

Those measure different things. Analytics counts what *this process* has observed since it
started, and trims its maps; `User.duelWins` is the lifetime total across every replica since the
account was created. They coincide only inside one pod's uptime for a player who started from
zero — so after any restart, and on every pod of a multi-replica deployment, the detector could
not fire. Pass 15 made the analytics side reachable; the comparison built on it was still inert.

The rate is the signal. A veteran with thousands of lifetime wins is not suspicious; twenty inside
one window is. The test asserts **both** directions deliberately, because asserting only the burst
would also pass against a naive "lifetime total > 20" that flags every long-standing player.

Known limitation, stated rather than hidden: analytics is per-pod, so an attacker spread across
replicas is undercounted — the caveat every in-memory detector in that class carries.

## HARDENING PASS 22 — 2026-07-27 (the social and replay surfaces, which nothing had audited)

Suite **756 → 775** (651 server + 124 client). Twelve findings from two parallel audits of
subsystems no earlier pass had touched — replay and persistence on one side,
friends/notifications/presence on the other. Eight are fixed here, with
**19 new tests and a 15-for-15 mutation audit**: every fix was reverted one at a time and the
test that claims to cover it was watched to fail.

The theme this time is different from pass 18-21's "features that did nothing". These features
did something — they just did it to the wrong data, or to data they had already destroyed.

### The replay surface: three callers that reset before reading

`SudokuBoard.reset()` clears `replayHistory`. Four methods use that list; three of them touched
it *after* resetting.

- **`jumpToMove(index)` threw on every call it did not reject, and wiped the board first.** The
  bounds check ran against the real history; `reset()` then emptied the list; the
  `subList(0, index + 1)` view was taken against nothing and threw `IndexOutOfBoundsException`.
  So a scrub-bar drag or a post-game review cleared the player's game and *then* failed. The only
  call that escaped was one that returned early. Fixed by snapshotting first — and copying rather
  than viewing, since `applyBatchMoves` appends to the same list as it goes.
- **`replayMoves()` replayed nothing and destroyed its own source.** The snapshot was taken after
  `reset()`, so it was always empty: the loop body never ran, not one line reached the output
  consumer, and the board had already been cleared on the way in. "Watch this game back" consumed
  the game.
- **`loadReplayFromJson()` cleared the board before validating the timeline.** A single bad field
  — an unknown `source`, a missing key, an off-board coordinate — destroyed the player's board and
  every move they had made, then threw `IllegalArgumentException("Invalid replay JSON")`. The
  caller sees a rejection and reasonably concludes nothing happened. Parsing now completes before
  anything is touched.

### undo/redo: an unbounded list and a half-applied pair

- **`redo()` appended to `replayHistory`; `undo()` removed nothing.** Fifty undo/redo cycles left
  53 entries where there had been 3. This is a live WebSocket path — a player tapping undo and
  redo while thinking grew a server-side list forever, and every export and replay afterwards
  showed the same move entered over and over. The board state stayed correct, which is exactly
  why nothing caught it.
- **Mirror mode: undo reverted the pair, redo restored half of it.** One player action writes a
  cell and its 180-degree twin, and undo already handled both. Redo popped one entry, so the
  primary came back and the twin stayed empty — a board state the game cannot otherwise produce,
  serialized to Redis and the database as-is, with the twin's move still sitting on the redo stack
  ready to fill a mirrored cell later with no visible cause.

`isCellEditable` also picked up a bounds guard. `EnhancedMove` already rejects coordinates outside
0..8, so this is defence in depth — but the method takes raw ints, is public, and is the first
thing every apply path calls. That exact shape shipped here once before, when `EnhancedMove`
allowed row -1 and the symptom was a raw "Index -1 out of bounds for length 9" over the WebSocket.

### Presence and delivery: two tabs made a player disappear

`GameSessionRegistry.playerSessions` mapped a player to a **single** session. Open a second tab
and it overwrote the first; close that second tab and the value-conditional remove matched and
deleted the entry outright — while tab one was still open and still playing. From then on, for the
whole life of that connection, the player was invisible: `isOnline` reported them offline to every
friend, and every player-targeted message (friend request, duel challenge, "You WON the duel",
achievement unlock, streak reminder) was dropped by `deliverToPlayerLocal`. `sendToPlayer`'s
boolean is swallowed by `MultiplayerBroadcaster`, so nothing logged a failure and the push fallback
never engaged either. Two tabs is the ordinary case.

Now a set, with the same per-key-locked `compute`/`computeIfPresent` shape as the pass-21
orphan-Set fix, presence clearing only when the last socket closes, and delivery reaching every
open tab.

### The friend graph was losing edges by design

`User.friends` is an `@ElementCollection`. Hibernate persists a change to one by **deleting every
row for that user and reinserting the whole set** — so `a.addFriend(b); save(a)` does not append an
edge, it replaces the list with a snapshot read earlier in the transaction. Two accepts touching
the same person concurrently each write a full snapshot and the second erases the first, with no
`@Version` to detect it. And because accept writes both directions as independent saves, losing one
leaves a **permanent one-way friendship** — visible in one player's list, absent from the other's,
with no pending request left to retry from and no UI path back.

Replaced with `linkFriend`/`unlinkFriend`: one statement per edge, so the outcome does not depend
on what else the transaction has read. `remove` had the same shape and got the same treatment.

Three more guards on `request`, each closing an unbounded path: you can no longer request someone
who is already your friend; a repeated request no longer re-notifies (the set deduplicated the
entry, but `notify` sat outside that check and fired unconditionally — an unlimited "X wants to be
your friend" stream, and the WebSocket channel that carries it has no cooldown); and a pending
inbox now has a ceiling. A block list is still missing — noted, not fixed.

### One phone, one account

`DeviceTokenStore` never de-duplicated a push token across players. A push token identifies a
*device installation*, not an account, so two accounts used on one phone register the same token —
a shared tablet, a handset sold on, a tester with two logins, or simply logging out and back in as
someone else. Only the forward map existed, so both entries survived and the previous owner's
notifications carried on resolving to that token: friend requests naming them, duel results, streak
reminders, all landing on the new owner's lock screen. Nothing errors, nothing logs, and the person
receiving them cannot tell the app it is wrong. A reverse token → player index now makes ownership
exclusive, on the Redis path and the degraded local path alike.

### A leak that needed a clock to see

`NotificationService.lastNotificationTimes` was write-only: every distinct player who ever received
a push added a key and nothing removed it, so the map tracked the total player population rather
than the currently-cooling-down one. It is not a cache — it is a five-minute window, and an entry
older than that window is indistinguishable from an absent one (`shouldSendPush` returns true for
both), which makes eviction behaviour-preserving by construction rather than a heuristic.

Worth naming why this survived a test class that already covered the cooldown thoroughly: **every
test in it ran inside a single instant.** A suite that cannot make time pass cannot observe an
entry failing to expire. The fix came with an injectable `Clock`, and the new tests advance it.

### Mutation audit — 15 of 15 caught

Each fix reverted individually, its test run, and the failure confirmed: the three reset-ordering
fixes, the undo retraction, the mirror redo pair, the notification sweep, three device-token
ownership rules, the four friend-request guards, the atomic edge writes, and both halves of the
multi-session registry fix.

### Still open after this pass

- `EventEngine.submitEventScore` has no callers — the whole event join/submit loop is unreachable,
  since `EventsController` exposes only `GET /api/events`.
- `getNextLogicalMove` / `getNextLogicalMoveAsEnhancedMove` disagree on their empty sentinel
  (`"No moves"` vs `null`).
- Registration returns distinguishable 409 vs 201 — recorded product decision, not a bug.
- `Constants.Difficulty.NIGHTMARE` asks for 55 removals, which no symmetric layout can satisfy.
- **New:** no move history of any kind is persisted — `moveHistory`, `redoStack` and
  `replayHistory` are all `@Transient`. So undo, redo, replay and jump all no-op after a cache miss
  or a restart. That is consistent rather than asymmetric, and changing it means designing history
  persistence rather than patching a method; recorded as a design gap, not fixed here.
- **New:** the friend graph has no block list, and `user_friends` has no unique constraint (the
  `NOT EXISTS` guard in `linkFriend` makes duplicates a narrow race, and a duplicate row collapses
  on read into the `Set` mapping — but the constraint would be better).

## HARDENING PASS 23 — 2026-07-27 (the background jobs, and a punishment loop)

Suite **775 → 793** (669 server + 124 client). Two parallel audits — every scheduled and
async job on one side, the whole auth/session/authorization surface on the other — plus
**18 new tests and an 11-for-11 mutation audit**.

The headline is not a data-loss bug or a leak. It is the game actively punishing a player
for something it could not stop re-reading.

### The anti-cheat scan was a punishment loop

`AntiCheatEngine.flagPlayer` is destructive and persistent: it **halves the player's
`cosmicDrip` in the database** and increments their lifetime `cheatFlagCount`. The scan runs
every 60 seconds, and six of its eight detectors called it unconditionally — only the
drip-spike and board-pattern checks carried any rate limit of their own.

What makes that catastrophic rather than merely noisy is that none of the evidence clears by
itself. `suspicionScoreMap` only decays inside `detectCheating`, on a *clean observation* — so
a player who crosses the threshold and then stops playing keeps that score. `moveRates` is
only reset when that player submits another move, so a stale rate above the threshold persists
indefinitely. `ipSolveCounts` only ever increments, nothing decays it, and the threshold is
**three solves from one address** — which any carrier-NAT or office address clears
permanently.

So one trip of one detector became a life sentence: starting at a million cosmic drip, halved
every 60 seconds, the player reaches **zero in about twenty minutes** and stays there, while
`cheatFlagCount` climbs by 1,440 a day per pod. Several detectors firing in the same pass
compounded it — each called `flagPlayer` separately, so a single scan could halve the balance
four times. And moderation could not undo it: `clearFlaggedPlayer` clears only the calling
pod's maps, so on a multi-replica deployment the other pods re-flag an exonerated player
within the minute.

Fixed with one cooldown consulted centrally in `flagPlayer`, before any state changes — which
also collapses a multi-detector scan into a single flag, the correct reading anyway: one scan
observing one player is one piece of evidence, however many ways it is described. Exoneration
clears the cooldown, so a genuine offence right afterwards is still actionable.

There was **no `AntiCheatSchedulerTest`**. That is how this shipped. There is one now.

### Every cosmic event fired twice

`EventEngine`'s constructor called `startCosmicEvents()`, installing three permanent
`scheduleAtFixedRate` tasks — and `EventScheduler` independently drives the *same* cycles on
the *same* periods. `EventScheduler`'s gap guard is its own in-memory map and cannot see the
engine's executor, so it never suppressed the duplicates.

Players felt it directly. `runDripShowdown` broadcasts to every connected client, so a
15-minute showdown announced itself twice per period per pod — 192 toasts a day instead of 96,
tripled across three replicas — and `runCosmicDuel` sent duplicate duel invitations, each
naming a different game id, to every eligible streaker. Board generation was duplicated at the
same rate against a three-thread pool.

`EventScheduler` is now the single driver.

### A rate limiter keyed on the thing the attacker creates

The WebSocket frame throttle was keyed on the `WebSocketSession`. A session is a resource the
caller creates at will, and **nothing capped how many they could hold** — so every new socket
handed out a fresh 20/s budget. One authenticated account opening 100 sockets to one gameId
got 2000 frames per second against that board, and every frame takes `GameLockManager`'s
cross-replica Redis `SET NX` + Lua `DEL`. That is precisely the lock starvation the throttle's
own comment says it exists to prevent: the board's real owner then failed every move, hint and
undo with "busy on another server instance" after a 3-second stall. A per-connection limit only
limits a caller who declines to open a second connection.

Separately, and needing no victim at all: a handshake carrying no `gameId` runs the generator
and **persists a `sudoku_boards` row**, and the handshake itself was throttled by nothing —
the frame bucket does not exist until a connection is established. A connect/disconnect loop
was unbounded database growth, which a concurrent-socket cap cannot see because each socket
closes before the next opens.

Now: budget keyed on the player, a cap of 8 concurrent sockets, and a separate much tighter
bucket on the handshake. The three are load-bearing together — none of them works alone.

### The one endpoint that never asked who was calling

`GET /api/game/active-of/{playerId}` took a player identity straight off the request and never
called `authService.getCurrentPlayerId()` — the only handler in the codebase where that was
true. Usernames are public (both leaderboards return them), so any authenticated account could
name any other and learn two things.

Presence, first: whether that person is playing right now — exactly what `FriendService`
gates behind an accepted friendship, so this was a way around the friends model entirely.
And then the live game id. For a casual board that id is an unguessable UUID, and being
unguessable is the **only** thing protecting it, because `getGameForReader` deliberately lets
anyone read a casual board so share links work. For competitive boards it returned ids of the
form `duel-<id>:<victim>`, disclosing live duels and who is in them.

Pass 9's audit named this endpoint as "a discovery aid for both" of the read paths it was
fixing, fixed those, and left the aid open. Access now requires that you are the player or
that you are friends — and refusal returns the same 404 as "not playing", since telling a
stranger they are not entitled to know still tells them the account exists.

### Nine jobs, one thread

No `TaskScheduler` bean, no `spring.task.scheduling.*` property — so Spring Boot's default pool
size of **one** applied and all nine `@Scheduled` jobs ran strictly serially. One of them is
not like the others: the anti-cheat scan pages 500 boards a minute with a `findById` per board,
and carries `@Retryable(maxAttempts = 3, backoff = 5000ms)` while rethrowing, so a failing scan
sleeps ten seconds on the scheduling thread and repeats the whole pass three times.

Sharing that thread is `MultiplayerBroadcaster.broadcastHealthPing` — the 20-second keep-alive
whose entire purpose is to stop proxies reaping idle gameplay sockets. While the scan holds the
only thread, the heartbeat does not fire, load balancers reap the sockets, and **players are
disconnected mid-game by a background job that has nothing to do with them.** The 5-minute
Redis sync and 30-second metrics update are delayed by the same amount, so a Grafana gap during
an anti-cheat stall looks like an outage.

### A scheduler that was never scheduled

`leaderboardRefreshScheduler` was a bare `Runnable` bean. Nothing consumed it — no
`@Scheduled`, no `TaskScheduler.schedule`, no `ApplicationRunner`; grepping the name found the
declaration and nothing else. It read as a working scheduler in review and had never run.

`refreshLeaderboard` is the only `@CacheEvict` for `topPlayers`, `leaderboardSummary` and
`publicLeaderboard`, and the only reset of the `scoreDeltas` window. So the leaderboard caches
were evicted by nothing but their TTL, and `pointsDelta` — documented in its own source as a
"recent" figure — silently reported the monotonically growing lifetime total instead. Deleting
the bean outright would not have failed a single test.

### Two more unbounded maps, same shape as last pass

`LoginAttemptLimiter`'s in-memory fallback was never swept: expiry was consulted only for a key
touched again, and the sole removal path requires a *successful* authentication for that exact
key. The key includes the username, which the filter base64-decodes out of the `Authorization`
header and which the failure listener records whether or not the account exists. So while Redis
is down — a supported degraded mode, and precisely when the pod can least afford it — an
unauthenticated caller looping `Authorization: Basic base64(<random>:x)` permanently allocated
an entry per distinct username, with no success ever arriving to free them. Heap grows until
the process dies. `RegistrationAttemptLimiter` has the same shape, milder because its key is
the client address alone; swept too.

Each fix reverted individually and its test watched to fail: the flag cooldown and its
moderation clear, the event self-start, all three WebSocket controls, the `active-of`
entitlement check, the login-limiter sweep, the scheduler pool size, and the leaderboard
schedule.

## CONFIRMED — verified by direct code reading (need a running server/Redis to execute)

> **Status as of pass 16 — all five are FIXED.** V1 (nested lock) and V3 (hint charged to the
> owner) were closed in the pass 5-11 live-playthrough work; V2 (`/end` replay farm) by the
> `rewardsGranted` guard in the same run; **V4 and V5 in pass 16**, by deriving the period from
> the board's id instead of the wall clock. Kept for the record of what the defect was, not as
> open work.

### V1 · P0 · Nested game lock → total gameplay outage whenever Redis is up
`GameLockManager.lock()` always calls `acquireRedis()` (non-reentrant `SET NX`). But `applyMove`, `getHint`,
`undo`, `redo`, `saveGame`, `resumeGame` all take the game lock and then call `getGame()`
(`GameService.java:231, 206, …`), which takes the **same** lock again. The nested `SET NX` finds the key the
outer call already holds, spins the full 3 s wait budget, then throws `IllegalStateException("busy on another
server instance")`. So in the intended multi-replica-with-Redis config, **every move/hint/undo/redo/save/resume
fails after a 3 s stall.** The tests miss it because they mock `setIfAbsent` to always return `true`. This is a
regression introduced by the 2026-07-10 "P2-NEW-2" hard-fail change.

### V2 · P0 · Infinite gem/XP farm by replaying `POST /api/game/{id}/end`
`endGame` only guards on `activeGames.remove(gameId) != null`, but `/end` first calls `getGame` (controller
L119) which re-hydrates the solved board from the DB into `activeGames`. The next `/end` re-hydrates and
re-fires `notifyGameEndListeners` → `EconomyService.onGameEnded`, which re-awards `difficulty*10 + cleanBonus`
gems + XP with no "already rewarded" flag. Loop `/end` on your own solved game to mint currency indefinitely
(also re-spams SmartDifficulty/achievements). Defeats the idempotency A-5 assumed.

### V3 · P1 · `GET /api/game/hint?gameId=X` charges the board **owner**, not the caller
`GameService.getHint(gameId)` charges `board.getPlayerId()` with no caller/owner/spectator check. An attacker
passing a victim's active gameId drains 5 gems per call from the *victim's* wallet and increments the victim's
`hintCount` (forfeiting their clean-solve bonus + CleanSolver achievement), while receiving the hint.

### V4 · P1 · Daily completion lost across the UTC midnight boundary
`DailyPuzzleService.onGameEnded` recomputes `date = today()` at solve time and requires
`playerGameId(today, playerId) == board.getGameId()`. A puzzle joined on day N but solved just after 00:00 UTC
has `today()==N+1`, so the ids never match → completion, streak, leaderboard entry and notification are all
silently discarded. Fix: derive the day from the board's gameId, not the wall clock.

### V5 · P1 · Weekly-tournament completion lost across the ISO-week boundary
`WeeklyTournamentService.onGameEnded` has the identical wall-clock-vs-board-id mismatch: a puzzle solved after
the week rolls over is never recorded, so it shows incomplete forever and the player can never be ranked.
